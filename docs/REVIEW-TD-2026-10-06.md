## Headline

1. **Little of this is "2027", but more than TNM.** Material 2026→2027 changes that touch a mapping conclusion:
   TNM category profiles (G3/G4: `coding:uicc` 1..1 and `coding:snomed-ct` slices), ECOG (`coding:loinc` gets a
   required binding, `focus` → primary tumour), the mandatory diagnosis category 55342001 and the
   `occurredFollowing` target now allowing `diagnose-primaertumor` (G14), the MTB interpretation value set
   (`mii-vs-mtb-interpretation-high-low` on ploidie/hrd-score/mutationslast/brcaness), `value[x]` slicing turning
   *closed* on `rna-seq`/`einfache-variante` snapshots, and, outside TD's notes, the new MTB **panel DeviceDefinition**
   profile (GRZ kit rows), the **diagnosis profiles** (Onko and MTB `diagnose-primaertumor`: `category:onkologie` 1..1,
   `bodySite.coding:icd-o-3` required-bound to `mii-vs-onko-icdo3-topographie`, morphology extension 0..*;
   `fruehere-tumorerkrankung` needs two categories), the Onko variant profile's HGNC switch to
   `mii-vs-onko-marker-gene-hgnc` (system `http://www.genenames.org/geneId`; MTB/MolGen keep `http://www.genenames.org`),
   and typed QC sub-extensions. Everything else TD wrote holds identically in our pinned 2026 packages, so the fixes can
   be applied now; the 2027 switch is a mapper change (categories, bindings, types), not just a pin move.
2. **Our table has systematic errors, partly caught by TD.**
   - MolGen canonicals: most MolGen profiles use the short URL (`…/modul-molgen/StructureDefinition/variante`,
     `…/diagnostische-implikation`, `…/molekulargenetischer-befundbericht`, …); only `genomic-study`,
     `genomic-study-analysis`, `molekularer-biomarker`, `molekulare-konsequenz` keep the `mii-pr-` form. RD rows cite
     `mii-pr-molgen-variante` (22 rows) and the **non-existent** `mii-pr-molgen-kopienzahlvariante` (19) /
     `-strukturvariante` (16): 57 rows with invalid target canonicals. Two of them (`priorRds[].diagnosticDate`,
     `.diagnosticResult`) also name the variant profile for DiagnosticReport elements and belong to the Befundbericht.
     Oncology and GRZ tabs are clean.
   - Stale Genomics-Reporting slice names on 28 variant rows (15 oncology, 13 RD): `dna-change`, `amino-acid-change`,
     `genomic-dna-change`, `genomic-ref-allele`, `genomic-alt-allele`, `variant-type`, `transcript-ref-seq`.
   - `dataAbsentReason` is invalid wherever `value[x]` is 1..1: ECOG (`unknown` must be obds code `U`),
     `variant-inheritance`, `coding-change-type`, `mode-of-inheritance`, `clinical-significance`. This reverses the
     NUM-OMICS resolution for ECOG. Omitting the (0..1) component is legal but lossy, see section A.
   - GRZ kit/sequencer/pipeline rows (12, MAPPED) cite `Procedure.device`, which does not exist in R4; the slot is the
     GR extension `genomic-study-analysis-device` (sub-extensions `device` → Device, `function`).
3. **TD is wrong or incomplete in seven places** (section D) — raise them Friday.
4. **MII already ships MV-GenomSeq artefacts** in the Onko package: logical model `mii-lm-mvgenomseq-onkologie`
   (2026.0.3 and 2027) and, new in 2027, `ConceptMap mii-cm-onkologie-to-mvgenomseq` (scope: OncologyCase only).
   Both are defective: all four TNM rows target `diagnosisOD.ECOGPerformanceStatusScore`; `TNMSchluessel` maps to
   LOINC 33732-9 (a grading code) labelled SNOMED; the Condition ConceptMap is empty; the LM leaves the follow-up and
   plan blocks unmapped. Our table should feed them — that *is* the "MV-GenomSeq-Spezifikation" route from his email.
