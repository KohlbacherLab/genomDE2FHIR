_Status: v0.3, 2026-10-09, after external adversarial review by codex (gpt-6.1-sol) and vibe, every adopted finding verified (see Review log). **Implemented 2026-10-09, two review-fix rounds 2026-10-09/10: see section 11.** Owner: KohlbacherLab. Scope: deliverables (a) pip converter, (b) FML structural mapping for HAPI/matchbox, (c) matchbox validation, all pivoted to the MII KDS 2027.0.0 ballot._

## 0. Scope and definition of done

| Deliverable | Definition of done |
|:--|:--|
| **(a)** `genomde2fhir` pip package | `pipx install genomde2fhir` plus the input gate `pipx inject genomde2fhir "genomde-dk-validator @ git+https://github.com/KohlbacherLab/genomde-dk-validator@v1.1.3"` (git-only; without it `convert` refuses to run unless `--no-input-check` is given); `genomde2fhir convert <file-or-dir> -o out/` turns one or many Datenkranz JSON files (KDK oncology, KDK rare disease, GRZ) into FHIR R4 transaction Bundles. Every **schema-valid** input converts; every schema-invalid input is rejected with a report (no silent normalisation). Bundles load into HAPI (2xx on first and repeated ingest) and validate against the 2027 MII profiles **or** against the explicitly declared local MV-GenomSeq profiles where MII has no conformant representation (consent domains, therapy response). The per-row disposition report (implemented / preserved / dropped / unresolved) is produced for every conversion |
| **(b)** FML structural mapping | StructureMaps + source logical models that matchbox `$transform` executes on a Datenkranz file; result is a transaction Bundle that HAPI ingests; parity with (a) on a graph-aware comparison with zero unexplained differences for the supported configuration |
| **(c)** matchbox validation | a pinned, reproducible `matchbox-2027` instance with the 2027 ballot stack and the local `de.genomde.mvgs` package; a harness that validates per resource and per bundle, ingests into a validating HAPI, classifies results by message id/expression (content / unavailable-terminology / waived package defect), and produces a report per corpus with implemented, preserved, dropped and unresolved counts |

Non-goals: OMOP; DNPM-format input; AdverseEvent (MedDRA); production terminology licensing; automatic switch of defaults to 2027 final.

### 2.1 Change analysis 2026 → 2027

Full per-module diff with element-level evidence and the 98 directly affected rows: `docs/2027-BALLOT-DIFF.md` (165 changed StructureDefinitions across 10 modules; 227 rows touched with transitive effects; reproducible with `scripts/diff_packages.py <module> <from> <to>`).

**Breaking for our output (must change at the switch):**
- Diagnoses (`mii-pr-onko-diagnose-primaertumor`, inherited by MTB; `fruehere-tumorerkrankung`): `Condition.category` mandatory with slice `category:onkologie` = SNOMED 55342001; the `onsetPeriod` *slice* is removed but `onset[x]` stays open (dateTime|Age|Period), whereas Seltene diagnoses close onset to dateTime|Age; `abatement` narrowed; ICD-O-3 topography required-bound on the coding (licensed terminology); morphology extension 0..*; new `dueTo` / `transformation-von`; `occurredFollowing` may target a primary tumour.

ICD-O-3 topography was already required-bound in 2026 (on `.code`); 2027 moves it to the coding.
- TNM categories: `value.coding` 1..* sliced into `coding:uicc` 1..1 and `coding:snomed-ct` 0..1 with invariant `tnm-sct-uicc-konsistenz` (SNOMED display must contain prefix + UICC code); a/r/y prefixes become modifierExtensions; `*-symbol` profiles retired; `component:multipleTumoren`.

- Therapies: `Procedure.performed[x]` closed to dateTime/Period with `performedPeriod.start` 1..1; `StellungZurOp` system corrected; seven onko ValueSets renamed; `basedOn:tumorkonferenz` (Procedure) and `MedicationStatement.basedOn:therapieempfehlung` added; `medication[x]` CodeableConcept only on recommendations; MTB `systemische-vortherapie.statusReason` system+code 1..1.

## 3. Reference mapping, representations and the correctness oracle

### 3.1 Fold Thomas' table into the CSVs (concurrent with everything else)
Section A of `docs/REVIEW-TD-2026-10-06.md`: canonical URLs, slice names, `dataAbsentReason` rules, MTB plan links, response source, fusions, GRZ devices. Rerun `/check-terminology`, regenerate the XLSX, push the sheet. Ballot comments (section B there, 17 items) go out by ≈ 2026-10-27 **in parallel**; neither blocks feasibility work.

### 3.2 Representation register (replaces "35 policy switches")
A small, documented set of representation decisions (`docs/REPRESENTATIONS.md`, mirrored as constants in code and FML), one entry per open issue, each stating: MII target (if any), the chosen representation, conformance status (MII-conformant / **local profile** / dropped-with-warning), and the ballot/ticket that could change it. Where MII offers **no conformant representation** the plan declares a local profile instead of pretending conformance:
- **MV-GenomSeq consent** (`mvConsent` domains/type/date): local profile `mvgs-consent` derived from core `Consent` (not from `mii-pr-consent-einwilligung`, whose `provision.provision.code` is required-bound to `mii-vs-consent-policy`). The embedded Broad Consent (`researchConsents.scope`, an opaque "MII Consent 2025.0.1" FHIR object per the KDK schema) is passed through with an explicit migration step to the 2027 profile (slice rename, versionless `meta.profile`, reference rebasing) and validated separately.
- **Therapy response**: `mii-pr-mtb-response-befund.method` is 1..1 RECIST/RANO and genomDE has no method → local profile `mvgs-therapy-response` derived from `mii-pr-onko-verlauf`'s base (core Observation) carrying response code, date and the data source; no invented RECIST.
- **ECOG 5 / notApplicable**: dropped with warning (reported as *dropped*, never as covered).
- **TNM**: SNOMED input → UICC coding through a reviewed, **edition-aware** SCT→UICC map maintained in `de.genomde.mvgs` (the shipped MII maps cover 3 of 35 SNOMED codes seen in valid synthetic inputs); unmatched items are preserved as a text-only fallback (`weitere-klassifikationen` with `code.text`/`value.text`) and reported as *preserved, not conformant*.
- Localization → MolGen consequence; LOH → open component; expression → present/absent + interpretation; SBS → COSMIC URI; segregation `biparental` → local code; recommendation type → local extension; CNV type → DNPM codes + local CS; GRZ devices → GR device extension (+ panel DeviceDefinition on 2027); metachrone → derived (2027 only); therapy strategy → `MedicationRequest.category` (example-bound, no wrapper; `RequestGroup.code` only for real combinations); GRZ Specimen → `SpecimenCore` + vetted BTO/UBERON→SNOMED type map (original code kept as second coding), no invented temperatures.

### 3.3 Correctness oracle
The CSV is the specification, not the test. Each implemented row gets: a stable row id (new `row_id` column, branch + path), a disposition per profile set (implemented / preserved / dropped / unresolved), and **observable assertions** (FHIRPath on the output bundle) plus enum/boundary fixtures. Coverage is measured by **instrumented emission**: builders record every `(source path → profile, element)` pair they emit; the test asserts MAPPED ⊆ emitted over the corpus manifests plus the synthetic coverage fixtures (`examples/synthetic-coverage-fixtures/`). The 31 MAPPED rows with placeholder targets are repaired in P0 (real canonical or demoted); demoting rows cannot raise the score because dispositions are reported separately. Bundle-level checks: required target-resource closure (e.g. every MedicationRequest has its `reasonReference:Primaertumor`), cross-reference resolution, no dangling `urn:uuid`.

### 3.4 What "profile set 2026 | 2027" really means
The 2027 deltas are structural, not just canonical. Each of the twelve must-do items is classified as (a) **canonical-only** → handled by the registry; (b) **structural, confirmed** (mandatory `category:onkologie`, `value[x].coding:loinc` binding, `performedPeriod.start`, consent slice renames, QC value types, closed `value[x]` on MTB molecular profiles) → builder/map branches keyed by profile set, built against the shape valid in **both** versions where one exists (e.g. always emit `valueCodeableConcept`, always set `performedPeriod.start`); (c) **contested / probable artefact** (TNM `coding:uicc` 1..1, MolGen snapshot closure, therapieplan ServiceRequest conflict, `lagerprozess` 1..*) → built to the 2026 ∩ 2027 intersection with a delta entry to flip at 2027.0.0 final. The 2026-runnable artefact remains the existing spine mapper plus the new package's spine; full dual-version coverage is not promised.

## 4. Shared architecture (simplified after review)

- **Input**: `genomde-dk-validator` as a library (`DatenkranzValidator`, `classify`) gates every file; the converter consumes **validated dictionaries** — no generated dataclasses. Exact corpus manifests (valid / invalid lists) are part of the test suite. Any compatibility normalisation for known-bad producers is a separate, opt-in layer with its own tests.
- **Source models for FML**: `scripts/schema_to_logical.py` generates **bounded** logical models (`DatenkranzOncology`, `DatenkranzRareDisease`, `DatenkranzGrz`) from the BfArM JSON Schemas, resolving `$ref`/`allOf`/`oneOf` explicitly and failing on unsupported constructs; embedded FHIR objects (`researchConsents.scope`) are declared as opaque `Element` and handled by a dedicated migration group.
- **Target registry**: `profiles.yaml` = dependency lock (package#version per profile set) + curated constants (canonicals, slice names, fixed codes, systems), generated from the packages **joined with the CSVs' `mii_profile`/`fhir_element` conventions**, and consumed by **both** the Python builders and the FML maps (the FML constants are generated from it, so the three wrong canonicals in today's map cannot recur). Tests: every canonical resolves in the package cache; a dependency walk of the four 2027 roots finds every package; the registry does not try to model elements.
- **Terminology**: ConceptMaps and local CodeSystems as FHIR resources in `mvgs-ig/` (packaged as `de.genomde.mvgs` so matchbox, the FML and the Python share them): localization→SO, TNM SCT→UICC (edition-aware), ECOG→LOINC, structureType→SO, inheritance→HPO, segregation→LL5489-1, strategy→Seltene CS, consent domains, CNV type, Befundkategorie, use-type, hospitalisation bands, COSMIC NamingSystem, biparental, study design, metachrone flag, Specimen type map.
- **Identity and idempotency** (defined before any builder is written): sender-scoped keys = `submitterId` + TAN (+ local ids inside the submission) → `uuid5` resource ids; every entry is `PUT Type/<uuid5>` (client-assigned ids, idempotent on re-submission), `fullUrl = urn:uuid:<uuid5>`, intra-bundle references use the same urn; conditional updates by identifier for Patient/Specimen shared across submissions; `submission.type` sets the per-submission Provenance.activity (v3-DataOperation: initial CREATE, correction UPDATE, followup/addition APPEND) and the key of per-submission resources (GRZ genomic study: the initial submission and its corrections share one, a followup/addition gets its own); every resource carries `meta.source` naming its submission (both paths); corrections never delete server resources: stale ones are found by `meta.source` and, on the Python path, by the per-submission Provenance targets (`docs/IDENTITY.md`, Known limitation); `test` is converted in a separate identity namespace with `meta.security` HTEST; GRZ↔KDK linkage via TAN-G/TAN-C is defined in `docs/IDENTITY.md`; sparse GRZ Patient updates must not erase clinical demographics (PATCH-like merge or separate Patient per stream, decided in phase 1). Tests: repeat ingest, reordered arrays, corrections, identical local ids from different submitters.
- **Bundle assembly**: transaction Bundle; `request.method/url` on every entry; `meta.profile` unversioned; one `Provenance` per submission (Python path; converter version, profile set, submission type, sender and routing agents, targets every resource of the bundle; earlier submissions keep theirs) and `meta.source` `urn:genomde2fhir:submission:<submitterId>:<caseId>:<date>:<type>` on every resource (both paths; each component percent-encoded, `docs/IDENTITY.md`).
- **Logging/PII**: no TANs or pseudonyms in logs (redacted ids); report files carry them only where the user asks; bundles at rest in `out/` are treated as pseudonymised patient data (documented handling for DIZ users); proxy TLS verification on with a pinned CA; local CodeSystems carry licence notes (COSMIC signature names are Sanger-licensed: NamingSystem + codes only, no display mirror).

- Validation verdicts: ERROR > FAIL > DATA-QUALITY > INCONCLUSIVE > PASS. ERROR = validation could not run (matchbox

  unknown code of an external code system that is exactly the value of an input field; HGVS the converter composes
  counts only when the transcript code (or accession and version), the gene symbol and the c./p. notation are each
  verbatim input values. A value-set error of a system the tx server cannot check is unchecked only when the value
  set admits the coding's system (`compose.include[].system`, looked up via matchbox `ValueSet?url=`); a coding of a
  system the value set does not include is content, never source. A reference / profile-match failure is a cascade
  only when its target, followed through its references, has a content/source/waived error of its own (counted
  there); a target that is only unchecked makes it unchecked, a clean target or one of the wrong profile makes it
  content. The same rule covers required slices discriminated by `resolve()`: their target profiles come from the

  failing reference) are reported as candidate, never failing.
