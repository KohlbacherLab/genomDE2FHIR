**M4 — Identity, idempotency and parity are mutually inconsistent as specified.**
Section 4 mandates deterministic `urn:uuid` (uuid5 over submission id + path) and "PUT with conditional identifiers for Patient/Specimen; POST otherwise"; section 6 requires the FML to emit the *same* Bundle. FML has no uuid5 (the Java engine's `uuid()` is random v4 at best), so (i) parity can only hold with an id-stripping canonicalisation that the plan never defines, and (ii) the FML path re-run produces new ids → re-POST duplicates everything except Patient/Specimen. The E2E report already documents this failure mode ("HAPI pollution: repeated runs POST new resources each time"). The identifier systems for genomDE IDs (tanC/tanG, donor pseudonyms, sample ids) are an *open* MVGS-IG item (REVIEW-TD section C) with no named policy. **Bites:** B2/B6, section 4's linkage rules, any re-submission contract. **Fix:** define the identity model first (which resources get conditional creates; which identifier systems), prefer source-derived ids, and define the parity canonicalisation (strip `fullUrl`/`id`, sort entries) plus the re-submission contract explicitly.

**M5 — The `--profile-set 2026|2027` switch cannot work as described; "keep 2026 runnable" is not real for the new package.**
The plan says "Canonical URLs are version-independent; only element constraints move" and presents the switch as a registry concern. But the 2027 deltas are *structural*: TNM `coding:uicc` 1..1 + retired `*-symbol` profiles, the Consent base switch, closed `value[x]` slicing, mandatory `category:onkologie`, `performedPeriod.start` 1..1, renamed consent slices. A canonical-version registry cannot express "emit a `category:onkologie` slice with pattern 55342001 only in 2027". Builders will need `if profile_set == 2027` branches; the plan never says so, and A3's acceptance ("spine bundles validate clean against 2026 **and** 2027") implies dual-stack builders that nobody budgeted. **Bites:** every builder; rework when the ballot changes. **Fix:** classify each of the 12 must-do items as (a) canonical-only → registry, (b) structural → builder branch keyed by profile set, or (c) contested/probable-artefact → build to the 2026 shape + delta entry; state that the 2026-runnable artefact remains the existing 276-line mapper, not the new package.

**M6 — There is no single source of truth for target conventions, and the two existing paths already disagree on three canonicals — all three FML values are wrong.**

## 4. Verdict

The plan's analysis layer is excellent — the diff report, TD review and package pins all check out — but its execution layer is not yet buildable: the 2027 stack is missing ~15 transitive packages (including the one the Consent module derives from), terminology and MVGS-terminology work are sequenced after the phases that need them, and the identity/idempotency/parity design is self-contradictory. Build the package against the stable 2026∩2027 intersection now (keeping the existing mapper as the 2026-runnable artefact), treat the contested ballot items as a delta list to flip at 2027.0.0 final, and re-baseline the acceptance criteria around a versioned known-gap manifest — with those corrections this is a 10–11 week, three-deliverable plan that can actually ship.
